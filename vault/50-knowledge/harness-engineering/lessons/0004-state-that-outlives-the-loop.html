Lesson 4

State That Outlives the Loop

Lesson 2's harness retries cleanly — as long as nothing kills the process. This lesson asks the harder question: when the run ends without finishing, what is still on disk, and what did you just make someone type again?

Primary sources — read in full Twelve-Factor VI — Processes and Twelve-Factor IX — Disposability: processes are stateless and share-nothing, anything that must persist belongs in a backing service, and a well-built process can die at any moment without losing work. This lesson applies both to a harness. Session and cost semantics come from Claude Code's headless-mode docs.

The bug in Lesson 2's script

Look again at the retry mechanism in harness-min.sh:

session_id=""
prompt="$task"

for attempt in $(seq 1 "$max_attempts"); do
  ...
  [[ -n "$session_id" ]] && claude_args+=(--resume "$session_id")

That is correct, and it is also entirely in-process. session_id is a shell variable. So is the corrected prompt. They survive iteration two of the for loop and nothing else. Ctrl-C, a laptop sleeping, a set -e abort on an unrelated line, or simply exhausting max_attempts — and every one of them is gone.

For the CI-debugging case that barely matters: the task description came from a CI event and can be regenerated. It matters enormously the moment a human supplied the input. If the trigger for your harness is a person writing something into an editor, then "the process exited early" and "the person retypes their work" are the same event. That is not a robustness nitpick; it is the harness actively costing more than it saves.

Twelve-factor processes are stateless and share-nothing. Any data that needs to persist must be stored in a stateful backing service.

A harness has no database. Its backing service is the filesystem — which is fine, as long as you are deliberate about which files exist, and precisely when they stop existing.

Three tiers of harness state

Every piece of state in a harness sits in exactly one of these, and most design mistakes here are a piece of state sitting in the wrong one:

  • Ephemeral — shell variables, the assembled prompt string, anything in the process's memory. Dies at exit. Correct home for genuinely derived values; wrong home for anything a human authored.
  • Model-side — the conversation transcript, addressed by session_id. Survives process exit, but you do not own it: it lives in the CLI's session storage, is opaque to inspection, can be cleared, and cannot be edited to fix a mistake. Good for continuity, unacceptable as your only copy.
  • Durable — files the harness writes and owns. Survives exit, survives reboot, is greppable, diffable, and — critically — editable by the human when the agent got something wrong.

The rule that falls out: anything a human typed, and anything you will later need to account for, belongs in tier three. Everything else is an optimization.

The loop, as a diagram

The same trigger → agent → verify → gate spine from Lesson 2, with the state boundaries made explicit. The rail is no longer observability — it is the durability question, asked at every step:

durable state — survives process exit
TriggerA human edits a staged draft in $EDITOR. If a draft from a previous run is still on disk, that one opens — never a blank template.
State loadRead the sidecar: attempts so far, accumulated cost, and the session_id of the last run that didn't finish.
Context decisionRetain or discard. A stored session_id means resume; its absence means start fresh from the full instructions.
Agent loopclaude -p with an explicit tool allowlist — re-passed every run, never assumed to carry over.
VerificationA separate check on structured output: did the outward-facing action actually happen? Not "did the agent say it did."
Gate — passPublished. Now delete the draft and the sidecar — the last action taken, never the first.
Gate — failPersist draft, sidecar, and session_id. Report which fields were missing. Exit cleanly; the next run picks up here.

Ordering is the whole pattern

The single most important line in the prototype is a rm, and what matters is where it sits:

Temp-file instinct trap 'rm -f "$tmpfile"' EXIT — clean up on the way out, unconditionally. The reflex every shell scripter has. It guarantees no litter, and it guarantees that the one run you most wanted to recover is the one you destroyed.
Staged-draft pattern Delete only after verification confirms the outward action succeeded. Failure leaves a complete, editable draft exactly where the next run looks for it. Litter is the signal that work is outstanding.

This is write-ahead logging with the serial numbers filed off: record the intent durably, perform the effect, and only then discard the record. A harness that cleans up before it commits has chosen tidiness over the user's work.

One consequence worth stating plainly — the leftover file is not a failure artifact to be swept up by a cron job. It is the queue. Its presence means "unfinished work exists," and the next invocation's first job is to notice that.

Retain or discard: what resuming actually buys

Having stored a session_id, you get a real choice on the next run, and it is worth being precise about the tradeoff, because the intuitive answer is wrong in both directions.

What resuming buys: continuity of reasoning. The agent already worked out what was wrong with attempt one. Resume and it still knows; start fresh and it re-derives that from scratch, possibly differently. When the rejection reason was subtle, this is worth real money.

What resuming does not buy: a lower bill. This is the counterintuitive part. Resuming replaces "resend a fixed instructions block" — which is a stable prefix, and therefore highly cacheable across separate invocations — with "carry forward a transcript that grows with every attempt." For a short task, that trade is a wash at best. Resume for continuity, not for cost; if someone tells you --resume is a token optimization, ask them to measure it.

When to discard deliberately: if the human's edit substantially changed the input, the prior transcript is not context — it is anchoring. A fresh session is the right call when attempt two is a genuinely different entry rather than a correction of the first.

Accounting across attempts

The reason the sidecar holds more than just session_id: per the headless docs, the JSON result's cost and usage fields describe that invocation only. They do not accumulate across a resumed session. So a task that succeeded on attempt three, read naively, reports the cost of attempt three and silently discards attempts one and two.

If you care what a unit of work actually cost — and on a metered workflow you do — the summing is the caller's job:

state="$(jq -n --argjson prev "$prior_state" --argjson cur "$output" '{
  attempts:       ($prev.attempts       + 1),
  total_cost_usd: ($prev.total_cost_usd + $cur.total_cost_usd),
  num_turns:      ($prev.num_turns      + $cur.num_turns),
  session_id:     $cur.session_id
}')"

Note that session_id is carried, not summed — it is a pointer to model-side state, not a metric. That single asymmetry is the whole file in miniature: tier-three storage holding both an accounting record and an address into tier two.

Field note — this will bite you on macOS Building the conditional resume flag, the obvious form is an array: resume_args=(--resume "$id"), empty when starting fresh. Expanding it as "${resume_args[@]}" under set -u aborts the entire run on bash 3.2 — still /bin/bash on current macOS — because an empty array expansion counts as an unbound variable. Confirmed at the prompt: bash: resume_args[@]: unbound variable. The portable form is "${resume_args[@]+"${resume_args[@]}"}". A harness that only fails on the fresh-session path is a harness that works in every test you bothered to run.

The prototype

Full script at assets/harness-durable.sh — a generic "human drafts an entry, agent formats and publishes it" harness, structurally identical to the diagram above. Its lineage is a personal journaling workflow where exactly this failure occurred: a required field was missing, the agent correctly refused to publish, and the draft evaporated with the temp file.

Two design choices inside it are worth lifting out. First, the tool allowlist is re-passed on every invocation rather than assumed to survive --resume; the docs are explicit about permission mode being restored but silent on tool allowlists, and a permission set that silently changes on retry is not something to discover in production. Second, the structured-output schema carries a missing_fields array alongside published:

schema='{"type":"object","properties":{
  "entry":{"type":"string"},
  "missing_fields":{"type":"array","items":{"type":"string"}},
  "published":{"type":"boolean"}},
  "required":["entry","missing_fields","published"]}'

That is Lesson 2's legible-observation principle applied to the human instead of the agent. A gate that fails with "not published" sends someone hunting; a gate that fails with missing: weight sends them straight back to the one line they need to fix.

Permutations from here

Once the harness owns a directory of its own state, several things that look like separate features turn out to be the same move:

  • Run journals. Lesson 2's events.jsonl already does this per-run. Keying it by unit-of-work instead of by process gives you the full history of a single entry across every attempt it took.
  • Subagent research stashes. When a subagent retrieves context — docs, schema dumps, API responses — writing it to ./state/research/<topic>.md and passing the path back, rather than the content, keeps the parent's context clean while the retrieval stays reusable on the next attempt. The parent decides what to read; the retrieval survives the process that performed it.
  • Decision records. An append-only decisions.md the agent writes to when it makes a judgment call ("chose to treat blank as unset"). Cheap, and it makes an unattended run reviewable after the fact.
  • Crash-safe writes. Write to a sibling path and mv into place. Rename is atomic on a POSIX filesystem; a direct write that dies halfway leaves a truncated draft, which is worse than no draft.

What this doesn't solve

Durable state is not durable correctness. Nothing here stops a harness from confidently persisting a bad draft and resuming it forever — the gate still has to be right, and Lesson 3's argument about who is allowed to judge the work still stands. Nor does it address concurrency: two invocations racing on one staged draft will clobber each other, and the fix is a lockfile, which this prototype deliberately omits for a single-user workflow. Multi-writer harness state is its own lesson.

Check your recall

1. Lesson 2's script resumes sessions correctly. What exactly does it still lose, and when?

Reveal

Everything held in shell variables — session_id and the corrected prompt — the moment the process exits for any reason other than completing the loop. Retries survive within one run; nothing survives across runs.

2. Why is the staged draft deleted after the publish rather than in an EXIT trap?

Reveal

A trap fires on every exit, including the failures you most need to recover from. Deleting only on verified success turns a lost entry into a retryable one, and makes the file's presence the signal that work is outstanding.

3. Does --resume reduce token spend? Why or why not?

Reveal

Not reliably. It trades a stable, cacheable instructions prefix for a transcript that grows each attempt. Its real benefit is continuity of the agent's reasoning about the earlier failure, not cost.

4. A harness reports total_cost_usd from a run that succeeded on its third attempt. What is wrong with that number?

Reveal

It covers that invocation only — the cost fields do not accumulate across resumes — so attempts one and two are silently missing. The caller has to sum them in its own durable state.

5. Which tier does session_id live in, and which tier does it point at?

Reveal

Stored in tier three (a durable file the harness owns); points at tier two (model-side transcript storage the harness does not own and cannot edit).
