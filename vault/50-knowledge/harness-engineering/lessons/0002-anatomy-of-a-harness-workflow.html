Lesson 2

Anatomy of a Harness Workflow

Lesson 1 gave you what kind of constraint to apply. This lesson adds the missing dimension — where, in a running loop, each one actually sits — down to a script simple enough to run today.

Primary sources — read in full "What makes a harness a harness" (component taxonomy) and "Building Effective Agents" (the evaluator-optimizer pattern). This lesson's script uses the documented flags from Claude Code's headless-mode docs.

The four required parts of any harness

The taxonomy paper from Lesson 1 doesn't stop at defining "harness" — it names the parts every harness needs, and separates them from the parts that just make one better:

  • Agent Loop — interleaves reasoning, action, and observation; the model decides its next step from what it just observed, rather than following a fixed script.
  • Tool Interface — the actual mechanism to read files, run commands, alter the outside world. Without this, nothing the model "decides" has any effect.
  • Context Management — actively decides what enters and leaves the model's context, task-aware rather than a blind truncation.
  • Control Mechanisms — limits, verification, and deterministic actions that hold independent of whether the model cooperates.

Everything else — memory across steps, retry logic, observability, guardrails — is optional hardening on top of those four. Useful, sometimes essential for a given blast radius, but not what makes something a harness in the first place.

The workflow, as a diagram

Laid out in the order a real run actually executes, with each step tagged back to its Lesson 1 layer where one applies:

observability — every step logged
TriggerTask arrives — a CI failure, a cron tick, a human prompt.
Context managementAssemble only what's task-relevant into the prompt.
Layer 1 · Constraint harnessAgent loop starts, scoped to an explicit, narrow tool allowlist.
Layer 2 · Feedback loopTool interface executes an action; the observation returned is legible, not a raw traceback.
Control mechanismLoop repeats reason → act → observe until the agent stops or a turn/step limit is hit.
VerificationA separate check — deterministic test, or a second LLM call — decides if the task is actually done. Never the agent's own say-so.
Layer 3 · Quality gate — passDone. Nothing further runs automatically.
Layer 3 · Quality gate — failFeed the failure back as the next prompt (bounded retries), or escalate to a human.

Two things worth noticing about this shape. First, verification sits outside the loop, not inside it — it's a separate step the harness runs, structurally unable to be talked out of failing by the same agent that produced the work. Second, observability isn't a box in the sequence — it's the rail running alongside every one of them. If you only log the final result, you can't debug a run where the gate passed for the wrong reason.

Where "testing agent responses" actually lives

Two different things get called "verification," and conflating them is a common design mistake:

  • Deterministic verification — a test suite, a schema check, a query that confirms a row changed. Cheap, unambiguous, preferred whenever the task admits one. This is what the script below uses.
  • Evaluator-optimizer — when no deterministic check exists (is this translation good? is this summary faithful?), a second, separately-prompted model call grades the first one's output against explicit criteria, in a loop. Anthropic's own framing: "one LLM call generates a response while another provides evaluation and feedback in a loop."[1]

The design rule that matters more than which of the two you use: the thing that produced the answer must never be the sole judge of whether it's correct. That's true whether the judge is a shell command or another model call.

The simplest version that's still a real harness

No framework, no orchestrator — one bash script, using Claude Code's documented headless-mode flags directly. Every labeled comment corresponds to a box in the diagram above.

#!/usr/bin/env bash
# harness-min.sh — trigger -> agent -> verify -> gate
set -euo pipefail

task="$1"
verify_cmd="${2:-npm test}"
max_attempts=3
run_id="$(date +%s)-$$"
run_dir="./harness-runs/${run_id}"
mkdir -p "$run_dir"
log_file="$run_dir/events.jsonl"

log() {                                              # observability rail
  jq -nc --arg ts "$(date -Iseconds)" --arg event "$1" --arg detail "$2" \
    '{ts:$ts, event:$event, detail:$detail}' >> "$log_file"
}

session_id=""
prompt="$task"

for attempt in $(seq 1 "$max_attempts"); do
  log "agent_start" "attempt $attempt"

  # constraint harness: agent gets Read/Edit only — nothing else
  claude_args=(--bare -p "$prompt" --allowedTools "Read,Edit" --output-format json)
  [[ -n "$session_id" ]] && claude_args+=(--resume "$session_id")

  response="$(claude "${claude_args[@]}")"
  session_id="$(jq -r '.session_id' <<< "$response")"
  is_error="$(jq -r '.is_error' <<< "$response")"
  log "agent_result" "is_error=$is_error session=$session_id"

  if [[ "$is_error" == "true" ]]; then
    log "escalate" "agent call itself errored"
    echo "Agent call failed — escalating. Events: $log_file" >&2
    exit 1
  fi

  # verification: deterministic, run by the harness, not the agent
  if eval "$verify_cmd" > "$run_dir/verify-$attempt.log" 2>&1; then
    log "gate_pass" "verified on attempt $attempt"
    echo "Done — verified in $attempt attempt(s). Events: $log_file"
    exit 0
  fi

  log "gate_fail" "verification failed on attempt $attempt"
  prompt="Verification failed. Output:
$(tail -n 40 "$run_dir/verify-$attempt.log")
Fix it."                                             # feedback loop
done

log "escalate" "exhausted $max_attempts attempts"
echo "Exhausted $max_attempts attempts — escalating. Events: $log_file" >&2
exit 1

Full copy at assets/harness-min.sh in this workspace, syntax-checked and executable. Run it as ./harness-min.sh "fix the failing test in src/parser.ts" "npm test".

Notice what's not here: no framework, no queue, no separate evaluator model. That's deliberate — the workflow-vs-agent guidance from Lesson 1's sources applies to harness scaffolding too: "find the simplest solution possible, and only increase complexity when needed."[1] This script is a real harness by the taxonomy above (it has all four required parts) — it's just not an elaborate one. Elaborate comes later, driven by a specific activity's blast radius, not by default.

Check your recall

1. In the script, which line is the constraint harness (Layer 1)?

Reveal

The --allowedTools "Read,Edit" argument — it removes every other action from the agent's reach before the loop even starts.

2. Why does eval "$verify_cmd" run in the harness script rather than being one of the agent's allowed tools?

Reveal

So the thing being graded can't also grade itself — verification must stay independent of the agent's cooperation.

3. What would you lose if the log() calls were deleted but everything else stayed the same?

Reveal

The ability to debug a run after the fact, including cases where the gate passed for the wrong reason.

4. Name the two forms verification can take, from this lesson.

Reveal

Deterministic check, or an evaluator-optimizer second model call.
