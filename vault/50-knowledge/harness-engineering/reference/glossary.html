Glossary

The vocabulary this course adheres to. If a lesson uses a term below, it means exactly this — nothing looser.

Agent Harness
The software layer wrapping a language model that turns it into an agent able to act on a real system — it owns the tool interface, the control loop, and the constraints on what the agent may do. Distinct from an agent framework (a library for building harnesses), an SDK, an orchestrator (coordinates multiple agents), and an evaluation harness (runs an agent against benchmark tasks). — arXiv 2606.10106
Constraint Harness (Feedforward layer)
Rules that shrink the solution space before the agent acts — tool allowlists, permission scopes, rules files, type systems. Reduces what can go wrong by reducing what's possible at all. — Augment Code
Feedback Loop (Corrective layer)
Structured signals returned mid-task that let the agent self-correct — a failing test, a lint error with an actionable message, a tool response describing exactly what went wrong. The signal must be legible enough for the agent to act on it, not a raw traceback. — Augment Code, Anthropic
Quality Gate (Enforcement layer)
A deterministic check that blocks a bad outcome from landing, independent of whether the agent "listened" — CI, a pre-merge hook, a PreToolUse hook that hard-blocks a dangerous call. The layer that doesn't rely on the agent's cooperation. — Augment Code
Progressive Disclosure
The principle that a skill should load information incrementally — metadata first, full content when relevant, supplementary files only when needed — rather than dumping everything into context up front. — Anthropic
Blast Radius
The scope of damage a single agent action could cause if wrong — how many rows, how many services, how reversible. The central variable that determines how many harness layers a given operation needs.
Idempotency
A property of an operation: running it twice (e.g. after a retry, or an agent re-attempting a failed step) produces the same result as running it once, with no compounding side effects. Essential for any harness layer that retries automatically.
Admin Process (12-factor, Factor 12)
One-off tasks (migrations, backfills, console/REPL access) run as separate, disposable processes against the same codebase and config as the app itself — never folded into the running app's request path. Direct ancestor of "run backup/restore as its own scoped subagent invocation, not a side effect of the main session."
Disposability (12-factor, Factor 9)
Processes should start fast and shut down gracefully, and be safe to kill and restart at any time. Maps onto harness design as: an agent task interrupted or retried mid-way should leave the system in a safe, resumable state.
Agent Loop
The runtime cycle that interleaves reasoning, action, and observation — the model decides its next step from what it just observed rather than following a fixed script. One of the four required parts of any harness. — arXiv 2606.10106
Tool Interface
The mechanism that lets a harness perceive and alter an external environment — read files, run commands, modify a repository. Without it, the agent loop's decisions have no effect. — arXiv 2606.10106
Context Management
Actively deciding what enters and leaves the model's context — task-aware selection, not blind truncation. One of the four required harness parts.
Control Mechanism
Limits, verification, and deterministic actions that hold independent of whether the model cooperates — e.g. a bounded retry count, a hard turn limit. The harness-level ancestor of Layer 3 (quality gate).
Verification
A check, separate from the step that produced the work, confirming the task is actually done. Takes one of two forms: deterministic (a test suite, a schema check — preferred whenever possible) or evaluator-optimizer (a second model call grading the first). The producer must never be the sole judge.
Evaluator-Optimizer
A workflow pattern where one LLM call generates a response and a separate LLM call evaluates it against explicit criteria, iterating until it passes. Used when no deterministic check exists for the task. — Anthropic
Soft Boundary
A constraint living inside the harness process itself — prompts, hooks, regex, tool allowlists. Fast and cheap, but only as good as what its author anticipated; a gap in it fails silently. Necessary, never sufficient alone for a destructive action. — see Zenity, "system prompts are not security controls"
Hard Boundary
A constraint enforced by a system outside the harness entirely — a database role's missing write grants, checked by the database engine itself. Doesn't anticipate intent; checks a fact. The only kind of boundary a destructive action should ultimately depend on. — Railway
Skill (Claude Code)
A packaged, invocable set of instructions (a SKILL.md with frontmatter, optionally with scripts/resources) that Claude Code loads on demand. User-invoked (/name) or model-invoked (triggered by description match).
Subagent
A fresh Claude Code agent instance spawned to handle a scoped task, with its own context window and — critically — its own permissions, which are not automatically inherited from the parent agent. — Claude Code docs
Hook
A deterministic shell command the harness runs at a defined lifecycle point (PreToolUse, PostToolUse, Stop, SubagentStop, …), able to inspect, block, or react to agent actions. The primary mechanism for building quality gates in Claude Code specifically. — Claude Code docs
Durable State
Harness state written to files the harness itself owns, surviving process exit, reboot, and crash — as opposed to ephemeral state (shell variables, the assembled prompt) that dies with the process, or model-side state (the transcript behind a session_id) that persists but is opaque and uneditable. Anything a human authored belongs here. — Twelve-Factor VI
Staged Draft
A durable input file created before the agent runs and deleted only after verification confirms the outward-facing action succeeded — never in a cleanup trap. Its continued presence is the signal that unfinished work exists, making the next invocation's first job to notice it. Write-ahead logging applied to human input.
Context Retention
The per-attempt decision to resume a prior agent session (--resume) or start fresh. Retaining buys continuity of the agent's reasoning about an earlier failure; it is not a token optimization, since it trades a cacheable instructions prefix for a transcript that grows each attempt. Discard deliberately when the corrected input differs enough that the prior transcript would anchor rather than inform. — Claude Code docs
